# Permanent ROCKET Trace Fields Plan

## 1. Goal

The current ROCKET timing trace fields were added manually in generated backend files. That is useful for debugging now, but the changes are temporary because regenerating the ROCKET backend can overwrite:

- `variants/ROCKET/include/ROCKET_PerformanceModel.h`
- `variants/ROCKET/src/ROCKET_PerformanceModel.cpp`
- `variants/ROCKET/src/ROCKET_SchedulingFunction.cpp`
- generated trace/channel/monitor files used to carry `assembly`

To make the trace fields permanent, the same schema must be emitted by the code generators and supported by the CorePerfDSL/trace description flow. The permanent version should preserve the current timing CSV field names, order, and count exactly.

No simulator timing behavior should change.

## 2. Current Timing CSV Schema

The current ROCKET timing CSV has 67 fields.

```text
pc,instr,assembly,rd,rs1,rs2,imm,rs1_data,rs2_data,IF,ID,EX,MEM,WB,IF_n_Enter,IF_n_PC_Gen,IF_n_uA_PcCorrect,IF_n_uA_CacheBlock,IF_n_uA_PcPredict,IF_n_ITLB,IF_n_ICache,IF_n_BPU,IF_prev_ID,IF_ext_Pc_mp,IF_ext_Pc_pt,IF_ext_Pc_p,IF_ext_Pc_p_j,IF_ext_Pc_p_jr,IF_ext_Ic_out,ID_n_Decoder,ID_rs1_ready_cycle,ID_rs2_ready_cycle,ID_n_uA_OF_A,ID_n_uA_OF_B,ID_prev_EX,EX_n_ALU,EX_n_MUL_max,EX_n_MUL,EX_n_DIVDelay,EX_n_DIV,EX_n_DIVUDelay,EX_n_DIVU,EX_n_EXPass,EX_n_DTLB,EX_n_LSUReq,EX_prev_MEM,MEM_n_MEMPass,MEM_n_DCache,MEM_n_StoreCommit,MEM_n_Branch,MEM_n_FlushMem,MEM_prev_WB,MEM_ext_Pc_c,WB_n_Reg,WB_n_CSR,WB_n_WBPass,WB_n_LoadWB,used_rs1,used_rs2,used_rd,rd_ready_cycle,icache_miss,dcache_miss,icache_delay_cycles,dcache_delay_cycles,divider_delay_cycles,sim_misprediction
```

Field groups:

- Identity fields: `pc,instr,assembly,rd,rs1,rs2,imm,rs1_data,rs2_data`
- Final stage fields: `IF,ID,EX,MEM,WB`
- Scheduling-variable fields: all `<STAGE>_<variable_name>` fields from `IF_n_Enter` through `WB_n_LoadWB`
- Diagnostic fields: `used_rs1,used_rs2,used_rd,rd_ready_cycle,icache_miss,dcache_miss,icache_delay_cycles,dcache_delay_cycles,divider_delay_cycles,sim_misprediction`

Missing per-instruction scheduling variables are currently printed as:

```text
null
```

This `null` behavior should also be preserved permanently.

## 3. Current Field Sources

### Identity Fields

- `pc`, `rd`, `rs1`, `rs2`, `imm`, `rs1_data`, `rs2_data` come from `ROCKET_Channel`.
- `assembly` comes from the generated trace monitor/channel path and is read by `ROCKET_PerformanceModel` through `getTraceValueHook("assembly")`.
- `instr` is currently set manually in each generated scheduling function with `setInstructionInfo(...)`.

Permanent source:

- Keep these as generated channel/monitor fields.
- Keep `assembly` as a real string trace value, not a value reconstructed inside the timing model.
- Generate `instr` from the scheduling function or instruction metadata so it remains stable after backend regeneration.

### Final Stage Fields

- `IF`, `ID`, `EX`, `MEM`, and `WB` are generated timing variables in `ROCKET_PerformanceModel`.
- These are already natural permanent fields because the performance generator already emits timing variable storage and stage printing.

Permanent source:

- Keep final stages generated by the performance-model generator.
- Extend the generator's timing stream template so these stages appear after the identity fields, matching the current schema order.

### Scheduling-Variable Fields

These fields come from local variables in `ROCKET_SchedulingFunction.cpp`.

Examples:

- IF local variables: `n_Enter`, `n_PC_Gen`, `n_uA_PcCorrect`, `n_uA_CacheBlock`, `n_uA_PcPredict`, `n_ITLB`, `n_ICache`, `n_BPU`
- ID local variables: `n_Decoder`, `n_uA_OF_A`, `n_uA_OF_B`
- EX local variables: `n_ALU`, `n_MUL`, `n_DIV`, `n_DIVU`, `n_EXPass`, `n_DTLB`, `n_LSUReq`
- MEM local variables: `n_MEMPass`, `n_DCache`, `n_StoreCommit`, `n_Branch`, `n_FlushMem`
- WB local variables: `n_Reg`, `n_CSR`, `n_WBPass`, `n_LoadWB`
- Previous-stage inputs: `prev.ID`, `prev.EX`, `prev.MEM`, `prev.WB`

Permanent source:

- The scheduling generator should emit `recordSchedVar("<STAGE>_<variable_name>", value)` immediately after each local formula variable is computed.
- Previous-stage max inputs should be recorded as `IF_prev_ID`, `ID_prev_EX`, `EX_prev_MEM`, and `MEM_prev_WB`.
- For instructions that do not use a field, the generated performance model should print `null`.

### External-Model-Related Fields

These fields come from values used by scheduling formulas or safe trace getters:

- Branch/frontend connectors:
  - `IF_ext_Pc_mp`
  - `IF_ext_Pc_pt`
  - `IF_ext_Pc_p`
  - `IF_ext_Pc_p_j`
  - `IF_ext_Pc_p_jr`
  - `MEM_ext_Pc_c`
- ICache connector:
  - `IF_ext_Ic_out`
- Cache diagnostics:
  - `icache_miss`
  - `dcache_miss`
  - `icache_delay_cycles`
  - `dcache_delay_cycles`
- Divider diagnostic:
  - `divider_delay_cycles`
- Branch diagnostic:
  - `sim_misprediction`

Permanent source:

- Any stateful external-model call must be emitted once into a local variable.
- The same local variable must be used both for the original timing formula and for trace recording.
- Safe read-only getters, such as cache miss getters after the already-computed delay call, can be used for diagnostics.
- Do not add a second call to stateful methods such as `getPc_mp()`, `getPc_pt()`, `getDelay()`, `getXa()`, `getXb()`, or `getMulReady()` only for tracing.

## 6. Permanent With Caveat

### `sim_misprediction`

`sim_misprediction` can be kept permanently, but its meaning must be documented carefully.

Current meaning:

- It is read from the Rocket branch predictor trace state after `getPc_mp()` is evaluated.
- Because Rocket redirect effects are consumed when scheduling a later instruction, this value can describe a previous control-flow instruction rather than the instruction shown in the same CSV row.

Permanent recommendation:

- Keep the field name and current behavior for schema compatibility.
- Document it as simulator-observed misprediction state, not guaranteed branch-row-local truth.
- If exact row-local branch reporting is required later, add a new mechanism such as delayed row patching. Do not change the current `sim_misprediction` meaning silently.

## 7. Fields That Should Not Be Made Permanent Yet

The following field types should remain temporary or require new semantics before they become permanent:

- Exact stage blocker or max-term winner fields.
- Exact row-local branch misprediction patching.
- Cache set/tag/replacement-way fields.
- BTB, BHT, and RAS internal debug fields.
- Any field that requires calling a stateful external model method a second time.

Reason:

- They either are not in the current 67-column schema or require additional simulator/debug semantics.
- Adding them now would change downstream trace shape or risk changing simulator behavior.

## 9. CorePerfDSL Requirements

The permanent schema should be driven by CorePerfDSL and generator metadata rather than manual generated-code edits.

Required CorePerfDSL-level support:

- Keep trace values for:
  - `pc`
  - `rd`
  - `rs1`
  - `rs2`
  - `imm`
  - `rs1_data`
  - `rs2_data`
  - `assembly`
- Keep external model trace connections for branch/cache/register/divider values where needed.
- Add no timing-latency changes.
- Add no branch predictor, cache, divider, or pipeline behavior changes.

If CorePerfDSL cannot express `assembly` as a string trace value in the current parser, then the trace schema should still remain permanent by adding generator-level support for an instruction assembly string field.

## 10. If Timing Variables Change Later

The permanent implementation can still generate correct trace variables when CorePerfDSL timing variables or scheduling formulas change, but the generator must support two different modes.

### Stable Schema Mode

Stable schema mode keeps the current 67-column timing CSV exactly as documented above.

Behavior:

- Existing downstream analyzers keep working.
- If a previously known scheduling variable disappears from the generated formula, keep its column and print `null`.
- If a new timing variable or local formula variable appears, do not silently change the 67-column schema.
- New variables should be added only through an intentional schema update.

This mode is best for benchmark comparison and long-running trace analysis where CSV compatibility matters.

### Auto Schema Mode

Auto schema mode derives scheduling-variable columns from the current generated scheduling graph/formula.

Behavior:

- If CorePerfDSL changes the pipeline timing variables, the generator emits the new final timing variables.
- If the stage formulas introduce new local variables, the generator emits matching `<STAGE>_<variable_name>` fields.
- If old variables disappear, they disappear from the auto-generated debug schema or become `null`, depending on the selected compatibility policy.
- This mode reflects the current model most accurately, but the CSV header may change.

This mode is best for model development and debugging after CorePerfDSL changes.

### Recommended Default

Use stable schema mode as the default output for ROCKET timing traces:

```text
keep the exact current 67 fields and print null for unavailable variables
```

Add auto schema mode as an optional debug output if new timing variables need to be inspected after CorePerfDSL changes.

For final stage timing variables, the generator can safely adapt to CorePerfDSL changes because timing variables are already explicit model objects. For local scheduling variables, the generator must inspect the actual scheduling nodes/formulas and record the variables generated for those nodes. Hardcoding only today's ROCKET local variable list would not be enough.

## 11. Validation For The Permanent Version

After moving this instrumentation into generator support:

1. Regenerate ROCKET from the CorePerfDSL.
2. Build the backend/plugin.
3. Run the ROCKET trace command.
4. Inspect one generated `ROCKET_timing_*.csv`.
5. Confirm the header has exactly 67 fields.
6. Confirm the header order exactly matches the schema in this document.
7. Confirm every checked row has the same number of columns as the header.
8. Confirm `assembly` contains real assembly text, not `null`.
9. Confirm missing scheduling variables print `null`.
10. Spot-check representative rows:
    - `add`
    - `mul`
    - `div`
    - `lw`
    - `sw`
    - `beq`
    - `jal`
    - `jalr`
11. Static-check that these stateful methods are not duplicated for tracing:
    - `getPc_mp()`
    - `getPc_pt()`
    - `getDelay()`
    - `getXa()`
    - `getXb()`
    - `getMulReady()`

## 12. Recommended Permanent Implementation Order

1. Add generator-owned timing trace schema support with the exact 67-field order.
2. Add generated performance-model trace state and print/reset helpers.
3. Add generated channel pointer connection for identity fields and `assembly`.
4. Add scheduling-node instrumentation generation for local variables and previous-stage inputs.
5. Add safe external-model local capture generation for branch/cache/divider/register/multiply values.
6. Regenerate ROCKET and compare the generated timing header against this document.
7. Only after the regenerated output matches the current temporary schema, remove manual generated-code instrumentation patches from the workflow.

## 13. Main Risk Points

- Regeneration can overwrite current manual instrumentation until the generator emits it.
- `sim_misprediction` is not guaranteed to be branch-row-local.
- `assembly` depends on trace/channel generation, not only performance-model generation.
- Sparse scheduling variables require stable `null` handling; otherwise row length or field meaning can drift.
- External models can be stateful, so any permanent generator solution must avoid duplicate calls.
- Field order is part of the downstream interface and must be treated as stable.
- If timing variables change, stable schema mode preserves compatibility but may hide newly introduced variables until the schema is intentionally updated.
- If auto schema mode is used, the trace explains the current formula better but downstream CSV consumers must tolerate header changes.
